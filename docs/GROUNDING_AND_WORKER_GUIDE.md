# Grounding and parallel work without changing the question

Written 2026-10-18 at Rohan's request, following review of `2b41281` and `d3d697c`.
This is the lead's operational guide for the approved build, not another master plan or a new
recognition theory. `FULL_BUILD_PLAN.md` remains authoritative for the work order (§4), grounding
(§0), anatomy-rule review (§7), active-task/packet index (§13) and measurement/family contracts (§§14–15).
Rohan's words and the theory govern both documents. This guide adds no repeated human approval
requirement. The machine-enforcement work in §10 is proposed and has not been implemented here.

## 1. What has to survive a new session

The mechanism to preserve is specific: an anatomical fact and complementary lossy descriptions
constrain a native question; the resulting measurement supports an anatomical description and
narrows dependent questions. Cheap structural information determines where expensive work runs.
That is how efficiency and discrimination arise together. The task is useful, reasonably competent
recognition by general rules, not purification of each input mask, a calibration target, or perfect
recovery on every study. Exact later representation and AI/diagnostic work retain their stated
dependencies. The original conversation and proof pictures establish this meaning; this paragraph
does not replace them.

Three different checks are necessary:

| Check | Evidence | What it does not establish |
|---|---|---|
| Sources available and read | Actual complete source units, their versions, full exchanges establishing approvals, viewed figures | A path list, import, hash or reading claim does not prove understanding. |
| Assigned operation preserves meaning | Concrete producer → transformation → product → decision consumer, justified from anatomy and the task contract | A correct paraphrase of the thesis does not justify a different operation. |
| Result satisfies the assignment | Complete code review, real production handoff, addressed native pictures, appropriate tests and source-matched runs | Green tests, agreement between readers, pixel counts and performance reports do not by themselves certify anatomy. |

The point of the workflow is to make substitutions visible early and keep them from landing.
No document or model check can guarantee the absence of semantic drift.

## 4. Split work by settled meaning and real dependencies

One lead owns the production runner, shared semantics and final integration. Helpers return facts
and candidates; they do not tell the lead what Rohan means. Consultations follow the existing
independent-reading protocol, with no voting or averaging of interpretations.

| Lane | Suitable cheap work | Boundary |
|---|---|---|
| Evidence | Reconstruct an addressed native support; generate raw/lens/support sheets; validate geometry and source addresses | Report what was inspected and what remains uninspected. A trace or projection stays a pointer. |
| Wiring | Explicit arguments, adapters, publication, cache identities, save ordering and real read declarations under a chosen contract | No invention of a native selector, threshold, sample meaning or fake consumer. |
| Implementation | Encode the lead's exact reviewed short rule using existing shared measurements | No variant leaderboard or per-study rule patches. |
| Verification | Invariant tests, source checks, receipt comparison, actual-entry-point runs in isolated output roots | Do not weaken the contract or equate a gate with anatomical acceptance. |
| Integration | Lead applies and reviews one bounded increment against the current source | A test-only helper or uncalled module does not complete a production task. |

Parallelize independent evidence, bounded implementation and verification. Sequence jobs when one
needs another's accepted product. Shared code ownership also creates a dependency even when the
anatomical objects differ. Two workers should not independently invent the same profile or geometry
helper. Give one worker that shared operation and supply it to the others.

Use the existing task/attempt directories and isolated candidate copies. Workers do not edit the
shared runner, master plan, grounding files or canonical outputs. A helper that needs filesystem
tools works in an isolated checkout/copy with explicitly scoped permissions and outputs. Isolation
protects production; it does not replace semantic review. Do not reset or clean another agent's work.
Rohan's earlier broad API implementation permission remains recorded in HOW_TO_BUILD; permission
is not an obligation to delegate that full scope to every worker. These packets deliberately
assign narrower ownership, with production integration retained by the lead.

Do not copy the old SquishOS night-shift runner: its runbook explicitly marks it superseded for
coding. The current SquishOS coding line has its own script/harness contracts and readiness gate;
it is not evidence that an unattended knee-build factory is available. This project's approved
local Claude Max packet route is FULL_BUILD_PLAN §10. No framework migration is needed here.
The shared global routing owner now points unattended coding to `docs/runbooks/coding.md`,
with nightshift.md explicitly identified as historical; it is synchronized through SquishOS setup.

## 5. Prepare the packet before launching its worker

Use this template inside a fresh task directory. Fill every applicable field; an unresolved field
is visible, not replaced by a convenient proxy. Attach whole definitions and exchanges as separate
units or inline them whole. Inspect the rendered prompt before dispatch.

```text
TASK: <P task / increment, F row where applicable, packet revision>
ROLE: <facts / prepare evidence / implement chosen rule / verify>
AUTHORITY: <current request and complete governing exchanges, actual authors>
INTENT: <one plain anatomical or wiring question>
CONTRACTS: <input M IDs -> output M IDs; F row/task; exact full units supplied>
MEANINGS: <what each input provides; what it does not assert>
OPERATION: <chosen general rule/transformation, in order>
CONSUMER: <real function and decision; when the product becomes available>
SCOPE: <files/functions allowed; acquisition/slice/window and unknown exterior>
PRESERVE: <source readings, previous decisions, named states, provenance, retention>
FORBIDDEN SUBSTITUTIONS: <the task-specific tempting but different objective>
SOURCE BASIS: <HEAD plus dirty/unit hashes; data/frame/image hashes>
DEPENDENCIES: <packet revisions and products this attempt assumes>
VERIFICATION: <meaningful properties, caller paths, native evidence, intended differences>
RETURN: <complete units/patch, imports, tests/logs, source hashes, findings/uncertainty>
STOP: <bounded result; exact hand-back if the contract cannot be implemented>
```

The packet supplies relevant original theory and corrections, not just the lead's paraphrase.
For source/seed/calibration work include the full §1.2 correction and actual M07–M14 roles. For
P2a include §1.1 and the complete P2a contract; identify the chosen production consumer before
counting work. General project rules still apply to helpers. Do not fit a packet by truncating
its definitions or dropping qualifications: split the task or choose a resource that fits.

For **DEFINE NATIVE RULE**, evidence preparation may proceed while the selector is unset.
Implementation waits for the lead's chosen rule and FULL_BUILD_PLAN §7's already authorized
checks: Codex reviews the thesis/rule, the Fable API consult reads the actual picture sheet,
disagreement goes to Rohan, and he sees pictures at each family wave. Do not silently replace
that process with a text-only visual verdict, a new approval loop, or a majority vote.

For this procedure, a packet is **at risk of semantic substitution** when it introduces or changes
how an identity, slice, spatial region, source eligibility or calibration sample support is decided.
Such a packet first requests a short operation return: Reads,
Produces, Consumer, anatomical justification and the specific non-objective. The lead checks the
proposed operation against the supplied contract before requesting implementation. This can be
a separate cheap call. Pure wiring that implements an already settled §§14–15 contract without
changing those decisions does not need another conceptual consultation. Merely passing a context
argument remains wiring; if it changes a selector's meaning, use the semantic check.
It checks the assignment, not whether the worker can recite the project's slogans.

## 7. Supervise dependencies and invalidate promptly

Keep the single job table in the active packet named by FULL_BUILD_PLAN §13, using its handoff
template. A wave has no separate live-state file: group its jobs within that table. Worker attempt
directories retain complete immutable invocation/completion evidence and are linked from the table.
Use named states, for example `PREPARING`, `READY`, `RUNNING`, `RETURNED_UNREVIEWED`,
`VERIFIED`, `ACCEPTED`, `NEEDS_RULE`, `STALE_INPUT`, `WITHDRAWN`, `FAILED`.
Record transitions and reasons. These are suggested record names, not an existing state engine.

When a premise, relevant contract or source changes:

1. Identify every running and returned task that depends on it, including downstream jobs.
2. Stop affected work promptly. Mark its output ineligible for integration at its own path,
   even if a process cannot be stopped immediately. Verify termination when stopping it.
3. Keep the failed/withdrawn attempt and logs. Do not let a polished README launder its result
   into the current plan or an acceptance record.
4. Supply the corrected complete unit and a new packet revision; invalidate derived reviews
   and tests whose premises changed. Do not merely send "remember the thesis" to the old job.
5. Continue independent work whose inputs and meaning are unaffected. Recheck it before use;
   absence of a dependency must be established, not guessed.

A process using the wrong objective is already affected even if read-only. Its output can corrupt
later decisions. Do not wait for it to finish and plan to add a disclaimer afterward. Counts and
area reports remain legitimate observations under a correctly framed question; they do not become
forbidden measurements merely because a previous agent misused them.

Observe jobs through completion signals and compact status records; investigate missing progress
through actual process/output state. Avoid duplicate dispatches and constant rereading of long
transcripts. A source or permission problem is not a reason to relaunch the same failing prompt
indefinitely. Route semantic gaps to the lead; only the unresolved human decision goes to Rohan.

## 8. Integrate only what was actually checked

The lead checks the complete returned units and imports, and compares their stated operation to
the packet before applying anything. A worker's conclusion is a claim to verify, not a premise.
An independent reviewer receives the governing sources and actual candidate/evidence, not only
the worker's favorable account. Text reviewers report visual limits explicitly.

Check allowed-file scope and the original source basis. If integration HEAD advanced, compare
the affected units and dependencies. Rebase/reissue as needed and verify the integrated candidate;
a mechanically clean patch does not establish semantic compatibility. One integrator writes
production and canonical task state. Workers run into separate new output roots.

Use FULL_BUILD_PLAN §9's existing production acceptance sequence and §15.3's six statements.
Trace the real caller, sibling routes, producer timing, context cache keys, map offer and single
save. Reconstruct native support from actual addresses and inspect the acquired frame. Preserve
unknown, measured-empty, partial, ties and native/laid/projected distinctions. Inspect the current
CI gate and its advisories. Use source-frozen real-CLI runs rather than a standalone prototype
as evidence of integration.

Separate equivalent refactors from intended scope/semantic changes. The former preserve outputs;
the latter need an explicit changed-output account and reasonable native competence. Neither
requires a calibration target, pixel-count target, perfect intermediate mask or universal success.
Report actual visited work and downstream constraints; claim runtime savings only from appropriate
paired whole-operation measurements. A new array that nothing consumes is not a targeting result.

Acceptance records belong to the lead and retain the source pin, exact runs, actual inspected
images, changed-output account and limits. Update live state only in §13's active packet; change
the §13 task/packet index together if the active task changes. NEXT remains a pointer card.
Record dated acceptance evidence in the relevant MAP/RESOLVING record. Do not copy an unreviewed worker verdict into four authoritative
documents. No commit or push is implicitly granted by finishing an individual worker attempt.

## 9. Pause and resume without losing the live work

At a requested pause, stop new dispatches and bring in-flight mutations to an explicitly recorded
boundary. Complete or stop each affected process; retain output and logs even if verification is
incomplete. Record which returned candidates remain unreviewed. A clean pause need not pretend
the whole wave is accepted.

Use the **single handoff template in FULL_BUILD_PLAN §13**, populated only in the active packet
that section names. This guide intentionally contains no second handoff template. The same packet
holds the source basis, request, evidence links, next action, unknowns, verification still owed and
job table. Update §13 only if its active task ID or packet path changes, never to duplicate the
packet's detailed state. Preserve earlier packet revisions as dated evidence.

After compaction, reread the primary sources by §0, inspect live processes and input identities,
then resume that actual task. Do not rediscover the plan from an agent's summary or assume all
workers stopped when the lead's context ended. If a child itself compacted, re-ground/reissue
its bounded task before trusting continuation. Full logs are evidence, not a substitute for the
current task record.

## 10. Smallest useful enforcement build

The following is a proposed hardening order. Use existing packet files and launch wrappers where
possible; no new generic orchestration framework or anatomy rule engine is required. This guide
does not claim these checks already run in CI or at launch.

| Order | Mechanical check to add | Human/lead meaning check retained |
|---|---|---|
| G1 | Packet preflight checks required fields, resolvable complete units, input hashes, bounded ownership and real return paths; fail missing fields with named codes | Lead confirms the input/output roles and actual operation, not just a nonempty field. |
| G2 | Durable job record stores process identity, packet revision, dependencies and transitions; changed dependencies make affected results ineligible | Lead determines the semantic impact and stops/reissues those jobs. |
| G3 | Acceptance preflight requires current source basis, real-run evidence, addressed image evidence and §15.3's six statements; stale/withdrawn artifacts cannot land | Lead checks reasonable native competence and the intended production consumer. |
| G4 | Documentation check validates pointers, complete-unit preservation/classification and explicit supersession; changes to grounding invalidate affected packets | Read the whole changed units and their destinations. A mechanical checker cannot decide equivalence of meaning. |
| G5 | Fresh-context exercises use the concrete failure cases below, retaining answers and proposed next operations | Inspect explanations and operations per case. No aggregate "alignment score" becomes a truth oracle. |

Suggested failure cases for G5:

| Given | Required distinction and next operation | Drift to catch |
|---|---|---|
| A dated correction is absent from a cleanup keep-list | Keep operative/unknown content in required grounding; classify its actual meaning | Default unknown sections to history. |
| A padded rectangle spans almost the frame | State only that construction's result; keep the actual region/consumer capability open | Declare unbuilt tile or irregular regions useless. |
| A calibration falls and a rim loses pixels | Inspect meaning and native anatomy; repair a demonstrated producer/consumer conflation if present | Purify seeds to recover the preferred numbers. |
| Broad projected bone support reaches a new frame | Use it as location context; independently measure the native question | Treat projection/union as definitive native marrow or discard all uncertain source evidence. |
| A useful local lens differs near its crop boundary | Retain scope/offsets; judge native competence as an intended scope change | Prohibit targeting under the equivalent-refactor rule. |
| One key orientation is missing | Preserve a partial physical reference and the native descriptions available | Fill it with a centroid or claim volume from the planes. |
| Code passes focused tests but has no real caller | Return an unintegrated candidate and finish the actual handoff | Mark the anatomy/pipeline task complete. |
| A withdrawn task finishes after the lead compacts | Keep it withdrawn; re-ground live job dependencies before use | Read its new README as current accepted evidence. |
| Safe-mode text-only worker is given only filenames | Supply the complete relevant units explicitly or return missing input | Assume it loaded CLAUDE.md or viewed a PNG. |

These exercises should test proposed action and its justification, not literal recitation. Passing
them is evidence about those cases only. The ongoing safeguards remain bounded work, honest
source/evidence roles, visible dependencies and production acceptance under the actual thesis.
